# Novo continuous reconciliation audit

Date: 2026-08-11. Scope: code inspection only; no production behavior, schema, or migration was changed. `REAL` means the inspected path implements the stated behavior; `PARTIAL` means a bounded portion exists; `MISSING` means no implementation was found; `UNUSED` means an implementation exists but is not in the continuous reconciliation path; `BROKEN` means the present path cannot preserve the intended reconciliation invariant.

## Evidence boundary

Proven below is limited to repository source and tests. Provider configuration, deployed cron/queue schedules, OAuth scopes actually granted, and live Google/Todoist behavior were not inspected; statements about those are explicitly inferences. Searches found no Todoist webhook route, no Todoist cursor model/metadata field, and no Google `channels.watch` call or persisted channel/expiry. The only calendar webhook receiver is `app/api/webhooks/calendar/route.ts`.

## Activity and recommendation mechanics

`AiActivityRun` and `AiActivityEvent` are the appropriate user-visible operational trace: `lib/ai/activity.ts#createActivityRun`, `appendActivityEvent`, and `finishActivityRun` enforce owned runs and sequence ordering; `lib/ai/activity-contract.ts` defines recovery merge behavior. `app/api/cognitive/loop/response/route.ts#recordOutcomeActivity` emits verification/learning activity after a user recommendation response. This is not a provider reconciliation journal.

`BehavioralSignal` is closer to learning data, but its documented vocabulary is task/focus/routine events and its schema has no external event identity or uniqueness. `syncTodoistPlugin` emits aggregate, repeatable signals each run, so using it as a delivery ledger would double-count. `NovoSignalLedger` is explainability/provenance for plan facts, not an append-only event store: fingerprint is `(source, sourceRef, signalType)` and subsequent observations overwrite the fact's label/time.

The canonical Novo Loop recompute is `POST /api/cognitive/loop/plan`. It supersedes the prior active `ActionPlan`, creates a `RecommendedAction`, and records task/goal/check-in signals. It is explicitly user-requested and requires a cognitive state snapshot. It does not observe imported Todoist checklist items or calendars, so an external completion cannot reliably cause a current "Today" recommendation to be withdrawn or recalculated.

## Smallest safe reuse path and blockers

The smallest reuse path is to normalize each accepted provider change into **one idempotent reconciliation record**, then reuse existing domain surfaces rather than inventing a parallel recommendation engine:

1. Keep `ChecklistItem.sourceId` as the Todoist task reference and `CalendarEvent.googleEventId` (or choose `TimeBlock`, not both) as the Google event reference. Make the chosen per-user/provider external ID unique.
2. On a successful pull/webhook delivery, derive a bounded safe summary and write a `NovoSignalLedger` fact with `sourceRef = provider external ID`; use it for explainability/correction. Then update the single mapped local entity in the same reconciliation transaction. `upsertNovoSignals` cannot be reused unchanged for this: `lib/cognitive/signal-ledger.ts#upsertNovoSignals` uses the global Prisma client rather than an injected transaction client, so the boundary needs a transaction-aware helper (or equivalent direct transaction writes), as well as an expanded source vocabulary.
3. Emit `BehavioralSignal` only for deduplicated learning-worthy lifecycle transitions (for example, a first observed completion), not every poll. Reuse `AiActivityRun` for user-visible reconciliation status and `McpAuditLog` only for MCP-initiated writes.
4. Enqueue/request the existing plan-generation route after reconciliation only when its prerequisites are met; otherwise invalidate the current action/read model. Do not treat `GET /api/integration/today` as a recompute hook.

This reuse is blocked by: no durable provider cursor/delivery/idempotency store; no canonical calendar entity; no persisted watch metadata/renewal; `NovoSignalInput.source` excludes Todoist and the loop planner does not consume imported tasks/calendar facts; and current completion writes are best-effort without an outbox/retry state. A new reconciliation boundary must supply those guarantees before external events are allowed to affect recommendations.

## Test evidence and gaps

Proven tests: `tests/novo-loop-isolated.e2e.ts` covers Novo signal-ledger correction/exclusion, activity ordering/recovery, calendar proposal idempotency, MCP task mutations, and MCP recommendation outcome persistence. `lib/cognitive/__tests__/todoist-signal.test.ts` covers pure Todoist threshold calculations; `lib/platform-connectors/__tests__/google-calendar-connector.test.ts` covers connector signal behavior.

Not found: route-level Todoist import/completion reconciliation tests; Todoist webhook/cursor tests; Google watch registration/renewal tests; webhook-to-canonical-calendar reconciliation tests; duplicate/out-of-order provider delivery tests; or an end-to-end test showing an imported external completion updates Today/`ActionPlan`/`RecommendedAction`.

## Correction note — 2026-08-11

This report was corrected after review without changing product code. The Todoist plugin path is **PARTIAL** periodic polling, not `UNUSED`: `runDailyInsights()` calls `syncAllPlugins()` in `lib/inngest/functions/daily-insights.ts`; the protected `GET /api/cron/daily-insights` route invokes that daily path through `maybeRunDailyInsights()`; and `vercel.json` declares the cron schedule. Those facts prove source/configuration, while actual deployed scheduler delivery remains unproven. The Calendar webhook finding now records that its `calendar.events.list` call supplies neither `showDeleted: true` nor a sync token, making the existing cancellation branch unreliable even within its -7/+30-day query window. The reuse path also now states the transaction-client limitation of `upsertNovoSignals`.
